RUNBOOK: testing all thirteen exercises, locally then in Docker
Every command is run from the project root: ~/gen_ai_topics_practice
Copy one line at a time. Check the "Expect" note before moving on.


=====================================================================
PHASE A. Before anything runs
=====================================================================

=== STEP 1. Confirm you are in the project root ===

  pwd && ls -d [0-9][0-9]_* | wc -l

  Expect: a path ending in gen_ai_topics_practice, then 13.
  If you get anything else, stop and cd to the right place.


=== STEP 2. Confirm .gitignore is in place ===

  head -1 .gitignore && grep -c "^\.env$" .gitignore

  Expect: the first comment line, then 1.
  If the count is 0, your live keys are not protected. Fix that first.


=== STEP 3. Confirm the tooling is present ===

  uv --version && docker --version && docker info >/dev/null 2>&1 && echo "docker daemon OK"

  Expect: a uv version, a docker version, and "docker daemon OK".
  If the daemon line is missing, start Docker Desktop and try again.

  Then confirm both suite scripts are executable:

  test -x run_level_00_all_basic_test_suite.sh && test -x run_level_01_integration_test_suite.sh && echo "both suite scripts are executable"

  Expect: the confirmation line.
  If not:  chmod +x run_level_00_all_basic_test_suite.sh run_level_01_integration_test_suite.sh


=== STEP 4. Confirm the API key landed in all thirteen, without printing it ===

  for d in [0-9][0-9]_*/; do printf '%-34s %s\n' "$d" "$(grep -c '^OPENAI_API_KEY=sk-' "$d/.env" 2>/dev/null || echo 0)"; done

  Expect: thirteen rows, every one showing 1. (09 makes no model calls,
  but its .env carries the key anyway for uniformity.)


=== STEP 5. Note your starting credit balance ===

  Open platform.openai.com/settings/organization/billing/overview in a browser
  and write down the number. You will compare against it after each phase.

  Nothing to run here.

PHASE B. Local test sweeps. Level 00 (free tier) first, then Level 01

=== STEP 6. Dry run. Confirms the plan, spends nothing ===

  ./run_level_00_all_basic_test_suite.sh --dry-run

  Expect: thirteen "would run" lines, with 01_stale_index_replay marked
  [needs Docker services] and 03 / 13 marked with their Neo4j container
  names (neo4j-fruit-graph, neo4j-temporal-graph). No warnings about

=== STEP 7. The Level 00 sweep. All thirteen, free tier ===

  ./run_level_00_all_basic_test_suite.sh

  Expect: a results table, all PASS. A few minutes; the paid gates
  (GRAPHRAG_RUN_INDEX, TEMPORAL_RUN_INDEX) are off, so 03 and 13 run
  only their free tests. 01 starts Postgres via compose; 03 and 13
  start their Neo4j containers if needed (a first-ever start downloads
  plugins and takes a couple of minutes). All services are STOPPED
  afterwards - never removed.

  If anything FAILs, read the tail printed on screen, then dig in with
  the grep command the report gives you. Do not move on until you
  understand each failure.


=== STEP 8. Check what that actually cost ===

  Open platform.openai.com/usage and look at Cost for today.
  Compare against the number from Step 5.

  Nothing to run here.


=== STEP 9. Confirm nothing was left RUNNING (stopped is by design) ===

  docker ps && echo --- && docker ps -a --format '{{.Names}}\t{{.Status}}'

  Expect: no running containers from these exercises, but DO expect
  stopped ones to persist: neo4j-fruit-graph, neo4j-temporal-graph and
  01's compose containers, plus their volumes in docker volume ls. That
  is the policy, not a leak - the Neo4j volumes hold indexes that cost
  real money to build, so the suites stop containers and never remove

=== STEP 10. The Level 01 integration suite. This is the one that spends ===

  ./run_level_01_integration_test_suite.sh

  It asks "Proceed and spend real tokens? [y/N]" first - answer y.
  Expect: for every exercise, the full walkthrough (main.py walk) with
  real model calls, then pytest with BOTH paid gates exported
  (GRAPHRAG_RUN_INDEX=1, TEMPORAL_RUN_INDEX=1). On a first-ever run 03
  indexes and 13 ingests, which is the slow, costly part - watch it
  rather than walking away. On later runs both skip straight to queries
  and the whole suite costs cents.


=== STEP 11. Check what the integration run cost ===

  Open platform.openai.com/usage again.
  The delta since Step 8 is what the full paid tier cost, dominated by
  03's indexing and 13's ingestion if their databases were empty. Write

  Nothing to run here.


=== STEP 12. Rerun Level 01 to see the steady-state cost ===

  ./run_level_01_integration_test_suite.sh --yes

  Expect: all thirteen, and much faster on 03 and 13 than Step 10 was,
  because both skip re-indexing when their Neo4j databases already hold
  the graph. This is the number a reader re-running the repo will see.


=== STEP 13. Read the transcripts if you want the detail ===

  less test_run.log            # Level 00: full uv sync + pytest output

=====================================================================
PHASE C. Preparing for Docker
=====================================================================

=== STEP 14. Baseline your Docker disk usage ===

  docker system df

  Write down the numbers. You will compare after the builds so you know
  exactly what to reclaim.


=== STEP 15. Sanity check one build context ===

  du -sh --exclude=.venv --exclude=__pycache__ 02_hybrid_rerank_retrieval

  Expect: a few hundred kilobytes. This is roughly what Docker will send
  as the build context. If it reads in hundreds of megabytes, something
  is copying a virtualenv and the builds will be very slow.


=== STEP 16. Decide what you are actually validating ===

  Two different things, with very different costs:

    docker build   free, just time and disk. Proves the image assembles.
    docker run     runs "main.py walk", which makes real API calls -
                   the same spend again as the local run, per exercise.

  Recommendation: build the eleven that have Dockerfiles, run two or
  three. Building proves the Dockerfiles are correct, which is what a
  reader cloning the repo cares about. 03 and 13 have NO Dockerfile by
  design - their setup scripts and long-lived Neo4j containers ARE the
  containerised path - so they are excluded from this phase. Running
  eleven full walkthroughs a second time is the same money for
  information you already have.

  Nothing to run here.


=====================================================================
PHASE D. Docker, strictly one at a time
=====================================================================

Each exercise follows the same three steps: build, optionally run, then
delete the image before starting the next one. Never build two at once.


=== STEP 17. Set the exercise you are working on ===

  EX=02_hybrid_rerank_retrieval

  Change this line for each exercise and repeat steps 19 to 22.
  Do 01 last - it is the special case, covered in step 23.


=== STEP 18. Build it ===

  docker build -t "ex_${EX}" "./${EX}"

  Expect: a successful build ending in "naming to docker.io/library/ex_...".
  First build pulls the uv base image; later ones reuse it.


=== STEP 19. OPTIONAL - run the walkthrough in the container ===

  docker run --rm --memory=2g --env-file "${EX}/.env" "ex_${EX}"

  --rm deletes the container the moment it exits, so nothing accumulates.
  --memory=2g caps it, so a runaway cannot take the machine down.

  This spends money. Skip it for most exercises; use it on one or two to
  prove the containerised path works.


=== STEP 20. Delete the image before moving on ===

  docker rmi "ex_${EX}" && docker system df

  Expect: "Untagged" and "Deleted" lines, then the disk table. Watch the
  Build Cache row - it grows even when images are deleted.


=== STEP 21. Repeat ===

  Go back to step 18, change EX to the next one, and work through:

    02_hybrid_rerank_retrieval
    04_rag_eval_ragas
    05_pii_erasure_replay
    06_injection_defence_llm_guard
    07_model_routing_litellm
    08_bounded_agent_langgraph
    09_mcp_tools_and_scan
    10_observability_langfuse_otel
    11_semantic_chunking_two_llms
    12_disk_ann_diskannpy

  09_mcp_tools_and_scan is the cheapest one to actually run: it makes no
  model calls at all. Good candidate for step 20.

  12_disk_ann_diskannpy uses Python 3.11 rather than 3.12, so it pulls a
  second base image. Expect that build to take longer.

  03_graphrag_fruit_graph and 13_temporal_bitemporal_graphiti are NOT in
  this list: neither has a Dockerfile. Their containerised story is the
  long-lived Neo4j container each setup script manages.


=== STEP 22. 01_stale_index_replay, the compose one ===

  This exercise needs Postgres, so it uses compose rather than a bare
  container. Four commands, in order.

  Build both services:

  ( cd 01_stale_index_replay && docker compose build )

  Run the app against a healthy database:

  ( cd 01_stale_index_replay && docker compose up --abort-on-container-exit )

  Tear it down, removing containers, volumes AND the locally built image:

  ( cd 01_stale_index_replay && docker compose down -v --rmi local --remove-orphans )

  Confirm it is gone:

  docker ps -a && docker images | grep -i stale

  Expect: no containers, and no image line. The postgres:16 base image
  stays behind, which is fine - it is shared and worth keeping.


=====================================================================
PHASE E. Cleanup
=====================================================================

=== STEP 23. Remove leftover containers - EXCEPT the two Neo4j ones ===

  docker ps -a --format '{{.Names}}'

  Expect: neo4j-fruit-graph and neo4j-temporal-graph (stopped), plus
  possibly 01's compose containers. The Neo4j pair MUST survive this
  phase: their volumes hold paid-for indexes, and "docker volume prune"
  in step 26 only spares volumes attached to an existing container.
  Remove everything EXCEPT them:

  docker ps -a --format '{{.Names}}' | grep -v -e '^neo4j-fruit-graph$' -e '^neo4j-temporal-graph$' | xargs -r docker rm -f

  Then confirm exactly two remain:

  docker ps -a --format '{{.Names}}'


=== STEP 24. Remove any exercise images still present ===

  docker images --format '{{.Repository}}' | grep '^ex_' | xargs -r docker rmi

  Expect: Untagged and Deleted lines, or no output if you removed each
  one as you went.


=== STEP 25. Clear the build cache. This is the big reclaim ===

  docker builder prune -f

  Expect: a "Total reclaimed space" line, often several gigabytes. Build
  cache survives image deletion, which is why disk stays full otherwise.


=== STEP 26. Remove orphaned volumes (the Neo4j ones are safe IF step 23
was followed) ===

  docker volume ls
  docker volume prune -f

  Expect: reclaimed space, usually the Postgres volume from exercise 01.
  neo4j-fruit-graph-data and neo4j-temporal-graph-data are spared because
  their (stopped) containers still exist - prune only removes volumes no
  container references. If you removed those containers in step 23, STOP:
  pruning now destroys both graph indexes, and the next Level 01 run pays
  to rebuild them.


=== STEP 27. Confirm you are back where you started ===

  docker system df

  Compare against step 14. Images and build cache should be at or near
  the baseline; the two Neo4j containers and their volumes remain, which
  is the intended steady state of this repository.


=== STEP 28. OPTIONAL - reclaim local disk too ===

  The thirteen .venv directories are large. Remove them only if you are
  finished, since the next sweep will have to re-sync everything.

  du -sh [0-9][0-9]_*/.venv 2>/dev/null | tail -1

  To remove:  rm -rf [0-9][0-9]_*/.venv


=== STEP 29. OPTIONAL - reset generated exercise state ===

  Each exercise can clean up after itself. This removes indexes, graph
  output and redacted corpora, but leaves source and .env alone.

  for d in 03_graphrag_fruit_graph 05_pii_erasure_replay 12_disk_ann_diskannpy 13_temporal_bitemporal_graphiti; do ( cd "$d" && uv run python main.py clean ); done

  Note: doing this to 03 or 13 empties their Neo4j databases, so the next
  Level 01 run re-indexes and re-ingests, which costs money again. Leave
  them alone unless you want a genuinely fresh run.


=====================================================================
PHASE F. When you are ready to publish
=====================================================================

=== STEP 30. Final check that no secrets would be committed ===

  find . -name ".env" -not -path "*/.venv/*" | wc -l && grep -c "^\.env$" .gitignore

  Expect: 13 and 1. Thirteen key files on disk, all covered by one ignore rule.


=== STEP 31. Initialise git ===

  git init

=== STEP 32. Stage everything and check what git actually picked up ===

  git add -A && git status --porcelain | wc -l

  Expect: somewhere around 145 files. The number itself matters less than
  the order of magnitude: if it is in the thousands, .gitignore is not
  being honoured, so stop and investigate before committing.


=== STEP 33. Prove no .env is staged ===

  git status --porcelain | grep -c "\.env$"

  Expect: 0. Not 1, not 12. Zero.
  If this is anything other than 0, run: git rm --cached <the file>


=== STEP 34. Prove the lockfiles ARE staged ===

  git status --porcelain | grep -c "uv\.lock$"

  Expect: 13. uv's guidance is to commit lockfiles, and these exercises
  pin awkward versions, so anyone cloning needs them.


=== STEP 35. First commit ===

  git commit -m "Thirteen standalone exercises for the ten RAG problems"


=== STEP 36. Connect to the empty GitHub repo and push ===

  git remote add origin https://github.com/kaichaza/ten_new_things_we_need_to_fix_with_rag.git

  git branch -M main

  git push -u origin main


=== STEP 37. Verify on the web ===

  Open the repo in a browser. Check that no .env appears anywhere, that
  all thirteen folders are present, and that the README renders.

  If a key ever does reach GitHub: rotate it immediately at
  platform.openai.com/api-keys. Removing the commit is not enough.
